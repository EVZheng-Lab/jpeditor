# 谱面就地编辑（原样档）

> 在右边「排版」里直接改谱，不必回左边源码上找。分三步落地，本篇是**计划 + 判据**，
> 每步做完把该步的「现状」改成实现记录（阈值、反例、踩坑照仓库惯例往里写）。
>
> 状态：第一步 **已落地** · 第二步 **已落地** · 第三步 未开工
> 回归 `npm run build && node scripts/pick-check.mjs && node scripts/edit-check.mjs`
>
> 现在能点、能改的：**音符 / 歌词 / 标题 / 词曲署名 / 调号拍号**（两种格式），
> 外加 `.jpwabc` 的**小节线**。还不能点的见文末「不做的事」。

## 总则（三步共用，先定死）

- **源码是唯一真相**。不引入第二套编辑模型：谱面上的任何编辑，最终都落成
  「把源码某个区间换成另一段文本」，再由现有的实时重排把谱面重画。
  谱面对象（Chord / NoteElement / PageItem）一律是**派生物**，不承载用户意图。
  这条是整篇的地基——一旦允许「谱面改了但源码还没改」，撤销、保存、按乐句重排、
  导出全都要各自再想一遍一致性。
- **只做原样档**（`.jpwabc` 走 `JinpuPainter`、文本谱走 `PuPainter`）。
  展开档不做：那一档按 `PlayItem[]` 逐遍展开，同一个 Chord 在多遍里各出现一次
  （见 [架构与实现](../架构与实现.md) 的「展开 / 原样两档」），点选要额外带遍号，
  而它本来就是投影用的、不是编辑用的。混排与识别核对视图也不做（后者已有自己的点选定位，
  见 `src/editor/omrctl.ts`）。
- **两种格式各有各的源码映射来源**，这是两侧工作量差一个量级的原因：
  - 文本谱：AST 每个节点自带 `source: SourceSpan`（`src/pu/ast.ts:11-20`，
    偏移是**全文绝对**的），现成可用。
  - `.jpwabc`：**目前没有**。只有 OMR / 导入**自己生成**的文本才带 `JpwMeta.noteRanges`
    （`src/score/jpscore.ts` 序列化时顺带产出）；手写或打开的文件解析成 Score 之后，
    Chord 上不带任何源码位置。要新增，见下一节。

## 落成的形状：源码区间挂在 `PageItem.source` 上

**全仓一条路**，两种格式、两个方向共用（口径定义在 `src/common/source.ts::SourceRef`）：

```
解析器记下区间 ──► 模型（Chord.source / Chord.pitchSource / Lyric.source / Credit.source /
                      Score.titleSource，文本谱是 AST 自带的 SourceSpan）
              ──► 排版器挂到 PageItem.source（宽，命中用）与 PageItem.editSource（窄，改写用）
                  （挂在**该被整体点中的那一层**）
              ──► 铺页后 App._tagSources 走一遍页面树，给 <g> 打
                  data-src-from/to（宽）与 data-src-edit-from/to（窄）
              ──► 命中 = ev.target.closest("[data-src-from]")
                  选中/编辑 = editRangeOf(g)（有窄的取窄的）
                  反查 = 扫这些属性找包含光标的那个（按宽的）
```

这样一来**「能点什么」只取决于排版器给谁挂了 source**，与命中机制无关：
音符挂在 entry 组上（数字、八度点、减时线一起被点中）、歌词 / 标题 / 词曲署名各挂自己的
TextFrame。加一类可点的东西 = 在排版器里多挂一处，App 那边不用动。

**偏移在打属性时才算**（`view.state.doc.line(line+1).from + column`）——模型里记的是行列，
理由见 `common/source.ts`。

**不给 `PuPainter` 补几何 pick**：它不继承 `ScorePainter`，但本来就为播放高亮建好了
`noteItems` / `syllableItems` + `nodeMap`，把 source 挂上去、命中交给 DOM 自己做就够了。

### `.jpwabc` 的几何 pick 只剩两件事

`onPageClick` 里的 `pickPage` **不再管源码定位**，只留「记住从这里开始试听的和弦」与状态栏描述。
理由是踩出来的：**entry 组的包围盒含着它底下的歌词**，盒心常落在数字与歌词之间的空档上，
`pickPage` 在那儿是落空的——定位挂在 pick 后面时，点音符十次有三次没反应，
而且 pick 落空会 `return`，连带 DOM 那条路也走不到。现在定位先做、pick 后做。

## `.jpwabc` 的源码区间从哪儿来

### 坑：段落行不是原文的连续切片

`JpwFile.parse`（`src/jpword/jpwfile.ts:309-319`）收集段落行时**跳过空行与 `//` 注释行**，
`VoiceSection.parse` 再 `lines.join("\n")` 交给 ANTLR。所以 ANTLR 给的字符偏移
（`token.start`）与文档偏移之间**不存在固定差值**，中间隔着被丢掉的那些行。

**判据：不要试图用「段落起始偏移 + token.start」换算。** 改为逐行记账：

1. `Section` 加 `lineNos: number[]`，与 `lines` 逐项对应，在 `JpwFile.parse` 往
   `lines.push` 的同一处 `lineNos.push(原始行下标)`。
2. ANTLR token 的 `line`（1 基，段内）与 `column`（0 基）经 `lineNos` 换回**文档行号**，
   列号不变（行内没有被裁剪）。
3. 落到 Chord 上的记 `{ line, column, length }`（文档行/列），**不记绝对 offset**——
   偏移随上游任何一次编辑失效，行列由调用方（App）用
   `view.state.doc.line(n).from + column` 现算，与 CodeMirror 的文档状态同步。

### 挂在哪（四类，都在 jpw 那条路上）

- **音符**：`makeChord`（`src/score/jpwimport.ts`）拿得到 `noteCtx`，**记两段区间**：
  - `Chord.source` = 整个 `Note` 词素（`{6,}` 倚音、`(`、`)`、减时线、八度逗号都在这个 token 串里）
    → 挂 `PageItem.source`，**命中与光标联动**认它：光标停在 `7,__` 的任何一格上都该点亮这个音符。
  - `Chord.pitchSource` = **数字那一格**（`jpwimport.ts::pitchIndex` 按花括号深度跳过倚音/三连音/
    控制选项里的数字，取第一个 `0-7`/`x`/`X`）→ 挂 `PageItem.editSource`，**点选与就地编辑**认它。

  两段是拿具体动作换来的：用户在谱面上点的是**那个数字**，选中 `5_` 之后接着敲一个音高，
  减时线就跟着被换掉了（「不要连带修改到 `_`」）。反过来只留窄区间也不行——光标走到 `,__`
  上时谱面高亮会灭。所以宽的管命中、窄的管改写，`editRangeOf`（`editor/inlineedit.ts`）
  是唯一一处「取哪一段」的判断。
- **歌词**：`WordsSection.parse`（`src/jpword/jpwfile.ts`）是逐字符扫的，扫到哪儿就记哪儿
  （`WordsItem.source`），再由 `assignLrcSeg` 传给 `Lyric.source`。两处细节：
  **尾随标点并进前一个字时区间要跟着长一格**（`望。` 要整体选中）、
  **开头的 `“` 挪到下一个字时两边的区间都要跟着挪**（那段归一化在 parse 末尾）。
  `/`（这个音符不跟词）那种空项没有位置，也不该有——谱面上没有东西可点。
- **标题 / 词曲署名**：`TitleSection.valueSpans`（与 `values` 同键），记的是 `=` **之后**
  那一段（不含键名与等号）。→ `Score.titleSource` / `Credit.source`。
  一条 `WordsByAndMusicBy` 靠 `\n` 拆成两行署名时，**两行指回同一段原文**（原文本来就是一行）。

一律是**可选**字段：Score 也从 MusicXML 建（`src/score/musicxml.ts`），那条路没有源码可指。

文本谱那一侧全都现成——AST 每个节点自带 `source`；标题与词曲从前没有，
这次在 `applyMetadata` 里补了 `Metadata.titleSpans` / `authorSpans`
（顺带修了一处：调用方一直传 `column = 0`，于是 `bad-mode` 那类报警都画在行首）。

## 第一步：点选联动（不改谱，只定位）

点谱面上的字 → 左边源码选中并滚到那一段；反过来，光标停在某个词素上 → 谱面对应的字高亮。
**能点的不只是音符**：歌词、标题、词曲署名都算（两种格式）。

**命中面积**：数字墨迹本身很窄，点偏一点就落空。第一步先用 `<g>` 的自然命中试手感，
**手感不好再补透明命中 rect**（照 `omr/overlay.ts` 那份做）——先不预先加，
多一层 rect 会牵动导出遍历（`layout/walk.ts` 那四个消费者）。

### 防回环

两个方向是互相触发的，必须有闸：谱面点选 → 改 selection，**不得**再由 selection 变化回头
去动谱面高亮；光标移动 → 改谱面高亮，**不得**回头动 selection。
用一个 `_syncingPick` 布尔量在两处入口各挡一次。
另外 selection 变化**不算文档变化**，不触发重排——`App` 的重排是挂在 docChanged 上的，
别把联动挂到会引起 reload 的地方。

**实际落成的形状**：高亮只有 `_syncScoreToCursor` 一处做（两个方向同一条路，
点选那头只负责 dispatch selection），所以闸的作用是「dispatch 期间别让 updateListener
再进来一次」，随后由 `_selectCode` 自己补调一次 `_syncScoreToCursor`。
**文档变了那一拍不点亮**：重排是 200ms 延时的，那一刻的谱面还是旧的（`<g>` 已经作废），
高亮交给重排末尾那一次——`renderPages` / `renderPuPages` 结尾各补了一调，
这同时也是「重排之后高亮还在」的实现（SVG 整棵重建，靠对象引用记不住，
只能按当前光标重新找一遍）。

### 反查按选区的**起点**，不按 `head`

`_syncScoreToCursor` 拿 `selection.main.from` 去找图元。按 `head` 找是错的、而且是**偶发**的错：
`_selectCode` 选中一个词素时 `head` 落在**末尾**，而 `.jpwabc` 里相邻词素之间常常没有空格
（`2_1)`、`|1'.`、`|(6_`），末尾那一点正是下一个词素的起点，`_elAt` 的「严格落在区间内」
当场命中**下一个**——于是「右边高亮的字与左边选中的字对不上」，有没有空格决定它犯不犯。
光标（空选区）时 `from === head`，所以光标那条路一直是对的，只有点选/就地编辑提交后才露馅。
回归 P7 逐个点一遍紧挨着的词素，守「点谁高亮谁」。

### 高亮用哪个类

复用现成的 `.selected`（点选，`App.onPageClick` 已在用）。不新增类：
试听高亮是 `.playing`（`src/layout/painter.ts:72-78`、`src/pu/painter.ts:1374`），
两者可以并存且语义不同，再加第三种只会让样式表和三个排版器的高亮语义更难对齐。

### 验收

`scripts/pick-check.mjs`（照 `scripts/harness.mjs` 的引导写，起本地 Edge，样本内联在脚本里
——这一条不依赖 `testdata/`）守：P1 `.jpwabc` 点选 → 只选中数字那一格、P2 行号换算、
P3 文本谱点选、P4 双向与重排后仍在、P5 展开档不联动、P6 歌词 / 标题 / 词曲署名。

**带空行与 `//` 注释行的样本是必需的**——那正是 `lineNos` 这一层的理由，
不放进去回归就守不住它。

### 落地时撞出来的三处旧账（都不是这个功能引入的）

- **`App.onPageClick` 取 `data` 取错了对象**。`data` 挂在 **entry 组**上
  （`layout.ts::NoteEntry` 的 `this.group.data = this`），而 pick 命中的多半是组里那个
  `JpNumber`——它自己 `selectable`，于是 `target` 停在它身上、`target.data` 是 undefined。
  后果不只是本功能：`_selectedChord` 也一直没设上，**「点一下音符、从这里开始试听」
  点在音符数字上时根本不生效**（只有点到组里非 selectable 的子元素才碰巧成立）。
  现在改成一律从 `entryGroupOf(picked)` 上取；**视觉高亮仍挂在 `target` 上**，那是原本的观感。
- **`.Title` 段里的 `//` 注释行会把它之后的语法着色整体错位**
  （`jpword/tokens.ts::parseTitleTokens`）。那份 token 流的契约是**逐字符连续**、
  `editor/highlight.ts` 按 token 文本长度累加偏移；旧代码遇到非 `KEY = VALUE` 的行
  直接 `console.error("bad line")` 就丢掉，少吐一行，后面全错开。
  段落体里的 `//` **到不了 `TokenData.parse` 顶层那个注释分支**——那里是按段落整块切下来的。
  现在注释行按 `LINE_COMMENT` 吐、认不出的行按 `Unknown` 吐，都补上换行。
- **`.jpwabc` 的小节线线型与反复记号在谱面上整个丢了**——见
  [架构与实现](../架构与实现.md) 的「`.jpwabc` 的线型与反复有两种表示」。
  与本功能无关，是排查「识别到了 `|:` 但排版里没有」时顺出来的。
  回归 `node scripts/barline-check.mjs`。

## 第二步：就地编辑单个记号（`src/editor/inlineedit.ts`）

选中音符后双击（或直接敲字符）→ 在该 `<g>` 的屏幕包围盒上贴一个绝对定位的 `<input>`，
初值取源码区间原文，回车/失焦提交、Esc 取消。提交 = 一次
`view.dispatch({ changes: { from, to, insert } })`，随后现有实时重排自动刷新谱面。

判据与要留意的地方：

- **提交前先验，判据是「比较」不是「归零」**（`App.validate`）：拿改动前后各量一遍，
  **变差了才拦**。存量谱面里本来就有靠解析器的错误恢复才过的写法（文本谱也常带几条诊断），
  一刀切要求"零错误"会把合法的改动一起挡在外面。拦下时**不写进文档**、输入框标红、
  焦点留住——写进去谱面会整个空白，而用户手上没有回头路。
- **`JpwFile.fromString` 不够用**：`@` `{` `"` `abc` 塞进 `.Voice` 它照样返回非 null
  （ANTLR 的错误恢复把那些字符悄悄吞了，音符却已经没了）。真正看得出来的是**语法错误计数**
  ——为此加了 `jpword/parse.ts::countVoiceSyntaxErrors`（同一套词法/语法，但**把报错收下来**）。
  **正式解析那条 `parseVoiceText` 不许改**：它故意关掉报错、靠错误恢复兜底，
  存量谱面要靠这个才打得开。
- **别拿 `X` 当"非法输入"的例子**：`Jpwabc.g4` 的 `Pitch` 里有 `'X' UniChar?`，
  那是**节奏音符**，完全合法。回归里用的是 `@`。
- **改完之后高亮还在**不靠记下标：提交时把选区落在改完那一段上，重排末尾的
  `_syncScoreToCursor` 自然会照光标把高亮重新点上（第一步就铺好的那条路）。
- **提交前先收掉输入框**：它挂在页元素上，重排 `replaceChildren` 会把它一起端走。
- 每次提交都整篇重排（走现有的 200ms 防抖）。小曲子无所谓，长谱要看是否需要节流
  ——**先不预优化**，实测卡了再说。
- **入口只有双击**，所以点中一个字之后状态栏要说一句「双击可就地编辑」（`EDIT_HINT`）
  ——不说没人会去试。

### 改了没反应 = 重排失败但没出声（`1=F 2/4` 那桩「删不掉」）

`App.reload` 解析/导入/排版失败时**留着上一版谱面**（别把用户的活儿刷白，这条是对的），
但从前是一声不响地留着：源码改了、右边纹丝不动，看着就是「这个删不掉」，
真正的原因只有控制台看得见。现在三处失败都走 `_reloadFailed`，状态栏说一句
「X 失败，右边仍是上一版谱面：…」，下一拍排出来了再自己收掉。文本谱那条 `reloadPu` 本来就报。

踩出这桩的那条具体路径，两个毛病叠在一起：

- **`TitleSection.meter` 少一半就抛**：`KeyAndMeters` 写成 `1=F`（或被删空）时
  `km.split(",")[1]` 是 undefined，`.trim()` 当场 TypeError → `fromJpw` 挂掉 → reload 静悄悄退回。
  现在 `keyAndMeters` 把**空值当没写**（返回 null），`key` / `meter` 各自缺了就返回 null，
  由 `fromJpw` 落到默认的 `C` / `4/4`。
- **纸顶那块调号拍号本来就删不掉**：`painter.ts::keyMeter` 的内容取自 `measures[0]` 的调号拍号，
  与源码里写没写 `KeyAndMeters` 无关，所以源码删干净了它照样画一个凭空的 `1=C 4/4`。
  现在由 `Score.showKeyMeter` 说了算：`.jpwabc` 那条路按「`KeyAndMeters` 有没有非空的值」定，
  别的来路（MusicXML / OMR）默认印。**代价**：从前没写 `KeyAndMeters` 的手写谱会白得一个
  `1=C 4/4`，现在不印了——要印就把那一行写上。回归 E7。

## 第三步：键盘流（结构化编辑）

选中后不开输入框也能改：←→ 前后音符、↑↓ 升降八度、数字键 1–7 改音高、
`_` 减时、`-` 增时、`.` 附点、Backspace 删。

这一步与前两步的分别是：前两步都在**搬运原文**，这一步要**理解并重组 token**
（`.jpwabc` 一个音符 token 里塞着倚音 `{6,}`、弧 `(` `)`、减时线、八度逗号；
文本谱有 `&xx` 记号、和弦 `"hx:…"`、附点、增时线）。所以第三步要先有一个
**token 解析 / 重组的小模块**，两种格式各一份，与各自的 parser 共用判据、
但**不复用 parser 本身**（parser 面向整篇、报错即失败；这里要能在半截 token 上工作，
同 `src/pu/highlight.ts` 开头那段「高亮不复用 parse.ts」的理由）。

先不定更细的口径——第二步做完会暴露真正的手感问题，那时再定。

## 不做的事（写下来免得来回讨论）

- 不碰展开档、混排、识别核对三个视图。
- 不做拖拽改音高、不做鼠标画弧线之类的图形编辑。
- 不引入撤销栈——CodeMirror 自己的撤销就是撤销，编辑落到源码上这一点自动成立。

## 还不能点的（要加就照上面那条路各挂一处）

- **文本谱的小节线**：`PuPainter.paintBarline` 把线与反复点**直接摊在 root 上**、没有自己的组，
  挂 source 得先包一层 Group——那会改动页面树的形状（`layout/walk.ts` 那几个消费者、
  导出都要跟着看），为一个记号不值当。`.jpwabc` 的小节线有自己的 entry 组，已经能点。
- **和弦符号**：`.jpwabc` 装不下和弦；文本谱的 `"hx:…"` 是音符前面另一个词素，
  `NoteElement.source` 罩不着它，要另记一个区间。
- **文本谱的页脚**（`BL:`/`BC:`/`BR:`）：区间已经记下了（`Metadata.headerSpans`），
  但 `PuPainter` 眼下根本不画页脚，没有东西可点。
